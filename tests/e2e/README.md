# Isolated HTTP acceptance tests

Run `npm run test:e2e` (or `node scripts/e2e.mjs`) with Node 24.10 or newer. The suite owns a fresh temporary source snapshot, Wrangler process, ephemeral loopback port, generated keys, fictional accounts and D1 state. It never uses the existing service on port 8787, `.dev.vars`, local invitations, live provider credentials or a browser. Installed dependencies must already be available through `npm install`.

The harness applies every migration, starts the actual Worker, exercises cookie sessions and signed HTTP ingress, drives the scheduled recovery handler, deliberately crashes and restarts its own process, and reapplies migrations against persisted state. Mutating HTTP requests run once; tests assert exact status codes and deterministic replay outcomes. Read polling is bounded. Both successful and failed runs stop owned process groups and remove the temporary state.

Scenarios cover cross-account isolation, disabled-provider sign-in readiness, two-sided signed channel proof/confirmation/revocation, explicit saved memory, one-time and recurring reminders, quiet hours and pause/resume, exact simulated-calendar approvals, provider-outbound pause/restart recovery, human handoff, staff roles/claims/queued replies/release/revocation, full paginated exports beyond the latest 100 transcript messages, usage and account erasure with replay after restart. Staff roles exist only on generated fictional fixture accounts. Private fixture SQL may alter only the suite's stopped temporary database to exercise approval expiry without waiting ten minutes.

The compact report is `.local/e2e-report.json`, with pass/fail steps, timings, a source-snapshot digest and bounded redacted diagnostics. Reports contain no generated invitation, session, encryption or webhook secrets. `node --test scripts/e2e.test.mjs` checks guard and harness utilities without launching a service.

The suite also invokes the actual local backup CLI while its service is stopped. It takes the backup before an HTTP account erasure, obtains that confirmed erasure record from its stopped temporary D1 database, writes a separate fresh protected ledger fixture, and invokes the offline restore verifier. Assertions check that the erased user cannot return from the older backup, authentication and claims are cleared, outbound delivery is paused, and a fictional unknown-charge tombstone remains. The restored database is never served; this checks the local restore mechanism and fixture ledger, not independent production R2 durability or cutover acceptance.

Passing these tests establishes the tested local mock workflows. It does not establish browser rendering, real provider delivery, Apple approval, cloud deployment, live OIDC/OAuth acceptance or production recovery. Those require their own fixtures and explicit external acceptance.
