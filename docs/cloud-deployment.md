# Cloud configuration and acceptance

`scripts/configure-cloud.mjs` produces a complete standalone staging or production Wrangler configuration. It does not provision resources, upload secrets, deploy, register OAuth clients, validate provider credentials, enroll Apple Messages for Business or send any message. Staging and production use separate Worker names, D1 databases, queues/DLQs and private privacy-ledger buckets.

The generator requires explicit real resource identifiers. UUID validation proves shape, not that Cloudflare allocated the database. Resource names must begin `plause-staging` or `plause-production` for their environment. Production generation additionally requires the reviewed staging configuration and rejects reused origins, D1 IDs/names, queue names and privacy buckets. These static checks cannot detect aliases or copied secrets in separately managed provider accounts.

Current staging is password protected. Use canonical `.local/staging-preparation/wrangler.staging.password.json` for future changes, retaining `STAGING_ACCESS_ENABLED=true` and six required secret names. The older closed-signup config predates this wall and must not be redeployed. [Staging access](staging-access.md) records HTTP/cloud verification and pending manual browser acceptance.

Base required fields are `CONTENT_ENCRYPTION_KEY`, `OPENAI_API_KEY`, `AUTH_GOOGLE_CLIENT_ID` and `AUTH_GOOGLE_CLIENT_SECRET`. Staging protection adds private `STAGING_ACCESS_PASSWORD_SHA256`; the canonical current staging deployment has six secrets including `AUTH_SIGNUP_SUBJECTS`. Enable protection with `--protect-staging` only for staging. The hash is private, never a public var; malformed enabled configuration fails closed. Enabling cloud signup additionally requires private `AUTH_SIGNUP_SUBJECTS`, whose value is a JSON string encoding 1–5 unique exact verified Google `sub` values. The generator rejects missing/malformed/duplicate/oversized policies when enabled, and validates the field whenever supplied. Do not put subject values in public vars, documentation, readiness output or logs. The content key accepts either the original canonical 32-byte base64 key or the full versioned keyring. Generate independent encryption keys and use separate provider projects/clients for staging and production. Existing backup ciphertext may require all retained keys; see [privacy and restore](privacy-and-restore.md).

`AUTH_SIGNUP_SUBJECTS` controls new account admission only; returning sign-in and reauthentication do not require open enrollment. With `AUTH_SIGNUP_ENABLED=false`, no new account is created. Admission compares verified Google subject claims, never email/domain/display name. Operator roles remain separate.

`OPERATOR_BOOTSTRAP_SUBJECTS` is an optional string containing a JSON array of up to five explicitly selected Google subject IDs, for example the operator's verified `sub` claim. It is not an email allowlist. Treat it as private deployment configuration, remove bootstrap identities after durable grants are assigned where appropriate, and test that an ordinary account cannot obtain operator access. No operator ID or support policy is invented by the generator.

Register the exact sign-in redirect `${PUBLIC_ORIGIN}/api/auth/google/callback` with the Google identity client. Calendar OAuth uses a separately configured connection and remains off by default. Secret files must be regular files owned by the current user, mode 0600, and not symlinks or hard links. The generator validates their shape and required fields without printing or placing their values in the generated configuration.

## Apple transport opt-in

The web service can operate before Apple enrollment. To generate a Sunshine transport configuration, additionally supply `--sunshine-config-file <private-json> --apple-approved --support-covered`. This is an operator assertion, not automated proof of approval or staffing.

The private public-settings file must contain exactly `APPLE_BUSINESS_ID`, `SUNSHINE_SUBDOMAIN`, `SUNSHINE_APP_ID`, `SUNSHINE_APPLE_INTEGRATION_ID`, `SUNSHINE_WEBHOOK_ID`, `SUNSHINE_BOT_SWITCHBOARD_ID`, `SUNSHINE_AGENT_SWITCHBOARD_ID`, `SUPPORT_HOURS`, `SUPPORT_TIME_ZONE` and `SUPPORT_CONTACT`. `APPLE_BUSINESS_ID` is the actual public Apple brand UUID, distinct from the Sunshine integration ID; it is used to open the approved business in Messages. The contact is an actual HTTPS support URL. The secret file must also contain `SUNSHINE_KEY_ID`, `SUNSHINE_KEY_SECRET`, `SUNSHINE_WEBHOOK_SECRET` and a nonempty explicit operator bootstrap list. Secrets stay out of `vars`.

Apple proactive notifications remain false even with this opt-in. Read [the adapter contract](sunshine-messaging.md) and verify actual approval, account linking/consent, device rendering, closure/reopen behavior, delivery callbacks, uncertain-send reconciliation and staffed handoff before accepting that channel. A configured support schedule does not establish live staff availability.

Public first-contact onboarding has an additional explicit `--enable-messages-onboarding` flag, accepted only with the approved Sunshine configuration. It emits `ONBOARDING_MESSAGES_ENABLED=true` and a default `ONBOARDING_GLOBAL_DAILY_LIMIT=500` (valid range1–5000); without the flag onboarding stays disabled. It does not enable proactive reminders. Verify welcome, proof-received and linked notices, plus accountless same-thread human escalation, before public activation. See [onboarding](messages-onboarding.md) and [live setup and acceptance](live-acceptance.md). `npm run readiness -- --config "$PLAUSE_STAGING_CONFIG" --secrets-file "$PLAUSE_STAGING_SECRETS_FILE"` checks selected static inputs without making requests or printing their values.

Real automated deployment must use the reviewed guarded interactive TTY, never piped or noninteractive confirmation. The guard must abort on conflicts, unexpected questions or noninteractive fallback; never auto-confirm an overwrite. The private activation plan records this execution policy. Both approved real deployments used the guarded path and were independently verified. Offline dry runs alone remain non-activating.

Separate one-time resource provisioning/migration access from routine deployment and runtime access. For an existing Worker, Cloudflare's current Workers Editor role can deploy code/settings/bindings without granting direct access to the bound D1/R2 data. Creating a new Worker requires Admin; changing routes/custom domains additionally needs the affected zone's Workers Routes Write permission. Prefer access scoped to the particular Worker and account. Do not copy broad account-admin credentials into Worker secrets. [Current Workers roles and binding permissions](https://developers.cloudflare.com/workers/authorization/workers/).

D1 migration/query tooling needs D1 write access (`D1 Edit` in the API permission list); queue provisioning needs `Queues Edit`, while read-only inspection can use read permissions. Restrict account and resource scope where the service permits. The Worker uses its D1/Queues/R2 bindings at runtime instead of carrying a Cloudflare management API token. [Cloudflare API permission reference](https://developers.cloudflare.com/fundamentals/api/reference/permissions/).

Independent ledger export tooling needs only read/list access to the selected bucket. External object-writing tools should use bucket-scoped object permissions instead of account-wide R2 administration; use a separate identity for bucket retention/lock changes. The application never deletes erasure records. R2 Object Read/Write tokens are for the S3 API, whereas the Worker uses its native binding. [R2 authentication and scope](https://developers.cloudflare.com/r2/api/tokens/).

After reviewing the generated destination and obtaining authorization for the cloud changes, an operator can apply migrations and deploy with secrets using the selected protected files:

```sh
node scripts/wrangler.mjs d1 migrations apply DB --remote --config "$PLAUSE_REVIEWED_CLOUD_CONFIG"
node scripts/wrangler.mjs deploy --config "$PLAUSE_REVIEWED_CLOUD_CONFIG" --secrets-file "$PLAUSE_SELECTED_SECRETS_FILE"
```

These commands are **cloud mutations** and are not run by configuration generation or the local test suite. Provisioning, DNS, OAuth registrations and any provider costs need actual account access and an authorized deployment step. Avoid an initial unauthenticated or secret-incomplete deployment window; the combined secrets-file deployment is supported by current Wrangler. Never seed fictional local accounts into a cloud database.

## Operational acceptance

Treat a successful local bundle/test as code evidence. A deployed staging acceptance run must record the actual origin, release source fingerprint, migrations, resource IDs and secret-name inventory, then exercise real sign-in/reauth/logout, tenant isolation, replay rejection, memory privacy races, exact approval, queue restart recovery, global pause, handoff, failure feedback and erasure pending/recovery. Verify session cookies and auth callbacks over the actual HTTPS origin. Confirm cloud cron and DLQ behavior rather than inferring them from local mocks.

Exercise independent-ledger backup/restore in an isolated cloud database with the complete retained keyring. Restored data must stay `restore_locked` and outbound-paused until live erasures are replayed, stale credentials/bindings/context are fenced and post-backup billing/delivery uncertainty is reconciled. Provider credentials and quotas need explicit test calls only after approved activation. The code cannot manufacture enrollment, consent, legal-policy acceptance, staff coverage, DNS ownership, recoverability or provider billing evidence.
